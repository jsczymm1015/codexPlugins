# 默认交付：中文表格报告

这是每次测试和重新评估的默认交付格式，不是某个项目的临时模板。用户另有格式要求时以用户为准。

## 谁负责什么

Codex阅读事实、翻译业务场景并归纳原因和影响；Jev返回分类和置信度；本地渲染器确保数字和状态保持原样。不要把Codex推断包装成Jev给出的文字结论。Jev不能生成解释正文，也没有替你执行测试。

## 生成步骤

保留 `evidence.json`、对应的 `jev-review.json`。用apply_patch另建 `report-notes.zh.json`，内容仅用于本地报告，**不再上传，不额外调用模型接口**。对每条需求和案例提供易懂中文。

```json
{
  "title": "订单重复提交功能验证报告",
  "context": "本轮复用已有测试结果，仅重新评估；测试环境为隔离数据库，生产环境未验证。",
  "requirements": {"R1": "相同订单重复提交，只能产生一条记录"},
  "cases": {
    "C1": {
      "scenario": "连续提交两次相同订单",
      "expected": "数据库只有一条记录",
      "observed": "数据库出现两条记录，断言失败",
      "evidence_summary": "本次隔离数据库测试；数量断言预期一条，实际两条",
      "cause": "已确认重复提交产生了重复记录；具体原因仍需检查去重条件，不能仅凭现象断定。",
      "impact": "用户重复点击可能导致重复订单。",
      "action": "检查去重条件与唯一约束，修复后重跑连续和并发提交场景。"
    }
  }
}
```

全部ID必须与原证据匹配，不允许遗漏。每个案例必须有中文 `scenario/expected/observed/evidence_summary`。失败或异常还必须有 `cause/impact/action`，未执行或跳过必须有 `action`。不要修改原始状态来迎合中文描述。缺少证据时明确写“待确认”，建议写“建议/待执行”，不编造根因或声称已经修复。

```sh
python3 <skill绝对路径>/scripts/render_report.py \
  --input evidence.json --review jev-review.json \
  --notes report-notes.zh.json --output report.zh.md
```

没有成功的Jev结果时省略 `--review`，仍生成本地测试报告并显示“未评估”。新输出文件不得覆盖旧报告。脚本会验证评估的输入哈希、状态、计数和分类格式，防止把旧评估套到新证据。哈希不匹配时找到原始输入，不能绕过校验。脚本不读取密钥、不联网、不运行测试。

## 表格布局

| 表格 | 要回答的问题 |
|---|---|
| 结果总览 | 是否通过、多少已执行、多少失败、多少待测、Jev是否运行 |
| 需求逐项结论 | 每条业务要求验证到什么程度，相关案例结果是什么 |
| 全部测试明细 | 测了什么、应该怎样、实际怎样、根据什么判断 |
| 问题详情 | 什么原因、有什么影响、下一步怎么处理，哪些是推断 |
| 未验证与行动 | 哪些还没做、为何没做、补什么才能确认 |

每张表优先2至5列，长问题拆成两列表格，避免塞入源码或堆叠英文堆栈。保留案例ID用于追溯。不得仅输出原始JSON、英文枚举或数字置信度。

固定译法：passed=通过，failed=失败，error=执行异常，skipped=已跳过，not_run=尚未执行；covered=案例设计已覆盖（不代表通过），partial=仅部分覆盖，missing=缺少覆盖，insufficient=材料不足；implementation=业务代码实现问题，test=测试代码或断言问题，environment=运行环境问题，data=测试数据问题，unknown=原因尚不明确。

置信度展示为百分比并注明“不是正确率”。多个需求复用同一案例时，需求表行数不能累加为测试总数。Mock测试、真实SQL测试、真实调度、完整事务必须在中文证据说明中明确区分。聊天答复至少包括总览结果表、最重要的失败/待测说明和完整报告链接。
